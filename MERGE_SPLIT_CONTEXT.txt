1. WHAT THE AUDIO EDITOR IS TODAY
================================================================================
AudioEditorActivity has TWO tabs:

  Tab 0 — "Merge"  (TAB_MERGE)   -> join several songs into ONE output file
  Tab 1 — "Split"  (TAB_SPLIT)   -> pro timeline: split / delete parts / reorder

Tab numbering matters: TAB_MERGE is deliberately 0 and TAB_SPLIT is 1 because the
last-used tab is persisted in SharedPreferences ("audio_editor_prefs", key
"last_tab"). Keeping the numbers means an existing user's saved value still points
at the same screen it used to.

The editor is reachable three ways:
  1. Main screen -> Menu bottom sheet -> "Audio Edit" tile          (Split, current song)
  2. From any file manager: SHARE one or more audio files           (share sheet)
  3. Internal "+" buttons inside the editor itself                  (picker)

Output files always go to:  <shared storage>/aud_player/edited/
  (fallback chain: getExternalFilesDir("edited") -> filesDir/edited,
   see FFmpegAudioEditor.outputDir())

2.1 OWN LIST, EMPTY BY DEFAULT  (this was an explicit user request)
-------------------------------------------------------------------
Earlier the Merge tab listed the SAME list the Split tab uses (`sources`), which
is seeded with the song the editor was opened with. The user asked for it to be
EMPTY by default and to be independent:

    "in merger, dont add the currently playing song by default, it should be
     empty by default."

So there is now a SECOND list:

    private final List<Source> mergeSources = new ArrayList<>();
    private long mergeDurationMs;              // 0 while the list is empty

`mergeSources` is completely independent of the Split timeline's `sources`.
Consequence (a real benefit, not a bug): editing the Merge list NEVER clears the
Split tab's splits/deleted-ranges. That is why `resetTimelineEdits()` and
`EditorTimelineView.clearEdits()` were DELETED as dead code — nothing needs them
anymore.

Its own time axis is built by `rebuildMergeMap()` (same algorithm as the Split
`rebuildTimeMap()`), producing `mergeDurationMs`.

2.4 THE PROGRESS BAR IS TAPPABLE / DRAGGABLE  (explicit user request)
-------------------------------------------------------------------
    "merge er progress bar take clickable banao"

The bar is a thin (5dp) horizontal ProgressBar wrapped in a 22dp FrameLayout so
the hit target is comfortable. `handleMergeBarTouch` calls
`barArea.getParent().requestDisallowInterceptTouchEvent(true)` on DOWN (so the
enclosing ScrollView does not steal the drag), computes
`fraction = clamp(ev.getX() / barArea.getWidth())`, then
`seekMergeSourceTo(index, (long)(fraction * durationMs))`.

`seekMergeSourceTo(int index, long localMs)`:
  - if a preview player is already loaded on the SAME song -> seek in place, i.e.
    the ordered preview queue SURVIVES the scrub (it keeps playing into the next
    song afterwards).
  - otherwise -> stopPreview(); previewList = mergeSources; createPreviewPlayer(...)

2.7 DRAG REORDER
-------------------------------------------------------------------
The existing MANUAL drag system (no ItemTouchHelper) is reused, not duplicated.
There is a `dragMode` field: DRAG_PARTS = 0 / DRAG_SOURCES = 1.
The ⠿ handle in a Merge row reports DRAG_SOURCES; `finishRowDrag` then calls
`moveMergeSource(from, ins)` (same `ins = to > from ? to + 1 : to` conversion
already used for parts) and re-renders. `moveMergeSource` returns boolean and does
NOT render — the caller renders.
`positionDragRow` / `updateRowDragTargets` / `resetRowDrag` are list-generic and
were not touched.

2.8 EXPORT
-------------------------------------------------------------------
    runMergeJob():
      one Segment(0, mergeDurationMs) + explicit uris + boundaries built from
      mergeSources, then
      startJob(MODE_MERGE, uris, boundaries, segs, baseNameOf(mergeSources))

    startJob(mode, segments, name) is the old 3-arg form; it now delegates to a
    5-arg overload that passes sourceUris() / sourceBoundaries().

`FFmpegAudioEditor.runJobFromUri(Context, List<Uri>, long[] boundariesMs, int mode,
                                  List<Segment>, String baseName, EditListener)`
copies each source once to temp, then `doJob`:
  - computes each input's OWN container extension (stream-copying an m4a source
    into a ".mp3" target fails outright — this is why)
  - MODE_MERGE -> one output named `baseName + "_merged"` with the FIRST input's
    extension
  - stream copy (`-c copy`); on failure the existing automatic AAC re-encode
    fallback runs (`reencodedTarget`), producing .m4a
  - MODE_SEPARATE = 1, MODE_MERGE = 2, MODE_CUT was deleted (see section 4)
  - progress is folded across pieces+runs into one 0..100

5. PLAYBACK ARCHITECTURE — THE `previewList` PARAMETRISATION  (read carefully)
================================================================================
One shared `MediaPlayer` powers both tabs. Which list it is playing is recorded
in:

    private List<Source> previewList;   // null == the Split timeline (`sources`)
                                        // non-null == the Merge list

Every global-time helper goes through `activeSources()`:

    private List<Source> activeSources() { return previewList != null ? previewList : sources; }

`sourceIndexAt` / `toLocal` / `toGlobal` all use `activeSources()`.

GUARD RULE: in `playheadUpdater`, all work that touches the SPLIT TIMELINE is
wrapped in `if (previewList == null) { ... }`. This exists because
`timeline.skipDeletedForward()` clamps to the timeline duration — running it while
previewing the merge list would corrupt the hidden Split timeline. In Merge mode
the tick instead calls `updateMergeRowProgress(pos)`.

`updateMergeRowProgress(long globalPos)` gives only the CURRENT row a non-zero
progress (others are forced to 0). `resetMergeRowPlayback()` zeroes every bar and
resets every row icon to ic_play; it is called from `stopPreview()`.

`updatePlayButtons()`: sets playBtn icon to ic_pause/ic_play, then loops
mergeRowButtons setting ic_pause only for (previewList == mergeSources &&
i == previewSourceIndex), else ic_play; and sets seqPreviewBtn text to
"■ Stop" when previewQueue != null else "▶ Preview".

`stopPreview()` = releasePlayer() + clear the queue (+ resetMergeRowPlayback()).
`releasePlayer()` swaps the player WITHOUT dropping previewQueue, which is what
lets a sequence preview continue into the next source at a seam.

AndroidManifest.xml — AudioEditorActivity is now `android:exported="true"` with:

    <intent-filter>  ACTION_SEND           + DEFAULT + <data mimeType="audio/*"/>
    <intent-filter>  ACTION_SEND_MULTIPLE  + DEFAULT + <data mimeType="audio/*"/>

`sharedAudioUris(Intent)` handles ACTION_SEND (a single Uri extra) and
ACTION_SEND_MULTIPLE (`List` AND `Object[]` forms), and `streamUri(Object)`
accepts a Uri, a "scheme://..." String, or a bare filesystem path
(-> Uri.fromFile(new File(s))).

onCreate routing:
    fromShare && 1 file  -> load it into `sources`, open TAB_SPLIT
    fromShare && N files -> first file into `sources`, ALL of them into
                            `mergeSources` in the order they were shared,
                            rebuildMergeMap(), open TAB_MERGE
    no share             -> the old EXTRA_URI path, last-used tab from prefs

IMPORTANT: `android:exported="true"` is what fixed the earlier
`SecurityException: not exported` when launching the activity directly with `am
start`. Do not remove the filters without a replacement plan.
